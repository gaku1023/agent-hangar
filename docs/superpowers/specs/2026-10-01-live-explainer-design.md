# 実行中のセッションの右ペイン（いま何が起きているか）設計

## この文書の位置づけ

実行中のセッション画面の右ペインを、作業中に横目で見て「いま何が起きているか」が分かる説明に作り直す機能の設計である。
今の右ペインはターンの目次（利用者の指示を 1 行ずつ並べ、押すと左の Claude もその指示へ跳ぶ）で、目次はこの設計でも一番下に残す。
見た目の試作は `2026-10-01-live-explainer/` にある（`pane-layout.html` が最初の 6 案、`pane-layout-v2.html` が 3 構成と部品、`pane-choose.html` が 3 構成の比較）。
利用者が最終的に選んだのは、実物の記録で動く再生の試作（`.superpowers/brainstorm/` の `pane-player.html`）の A である。
再生の試作は利用者のセッションの本文を埋め込んでいるので、公開のリポジトリには入れず、手元にだけ置いてある。
実装が済んだら、本体の設計書 `docs/design.md` の該当箇所（セッション詳細、MCP のツール、指示の注入、決めた前提）へ内容を移す。

## 目的

今の右ペインは指示の一覧と、押したターンの生の返答しか出さない。
一方で、左のターミナルには Claude の最後の数手しか映らず、指揮役のセッションでは `Agent(…)` の 1 行の下で何十本ものサブエージェントが働いていても、その中身は映らない。
利用者は Claude が作った用語や、会話がどこで動いていつ止まるのかを追いきれないことが多い（explainer の試行で hangar の索引から作ったペルソナの「怪しいところ」）。

そこで右ペインは、ターミナルに映らないものを出す場所にする。
具体的には、ここまでの累積、何のためか、なぜ止まったか、どの層を触っているか、サブエージェント 1 本ずつの様子、作業がどこまで進んだか（コミット、push、main）である。
「いま〜している」という 1 行だけを出しても、それはターミナルの最終行の言い換えにしかならない。

うまくいった状態とは、利用者が左のターミナルを遡らずに、右ペインを 2〜3 秒見るだけで「何本が動いていて、何のために、どこを触っていて、どこまで来たか」を言えることである。

## 利用者の決定（2026-10-01）

- 読む場面は作業中に横目で見るときで、目的は何が起きているか分かることである。割り込むかの判断や、済んだかの検証は目的にしない。
- 説明の書き手は組み合わせ型にする。
  - 「何をしているか」は、hangar が transcript のツール呼び出しから決まった規則で作る。
  - 「何のためか」は、セッション自身が節目に MCP で書く。
  - 用語は、押したときだけ説明器（LM Studio か `claude -p`）が読み手に合わせて解説する。
- 構成は A（全部を上から順に）にする。上から、状態の灯、意図、指揮役の手、サブエージェント、触っている層、作業の居場所、目次を並べる。
- 意図は端末ローカルに置き、同期しない。
- 作る順番は、1 回目が灯、意図、指揮役の手、サブエージェント、目次の色帯である。2 回目が層と作業の居場所、3 回目が用語の解説である。

判断の経緯は次のとおりである。
最初の 6 案（目次に差し込む、いまを固定、タブ、時系列の段、用語帳、3 行だけ）を見せた後、Fable と 2 回壁打ちして前提を改め、3 構成（A、文字を使わず形で、止まった時だけ大きく）に絞った。
利用者は情報量の多い試作では判断できず、9/20 のセッションの実物の 22 分（指揮役 1 本とサブエージェント 4 本、306 手）を再生する試作で A を選んだ。

## 範囲の外

- 区切りでの深い説明（mizchi/explainer の型で、出力を貼り、未検証を明記した資料を作るもの）。1 本に 40〜70 分かかるので、別の機能として扱う。
- 割り込みの提案や、完了の検証（テストが通ったかの判定、「済みました」の中身の照合）。
- 実行していない過去のセッションの画面。過去のセッションは今までどおり transcript を出す。
- 権限待ちと質問待ちの区別のうち、質問でない待ち。今の live の状態は `waiting` の中身を持たないので「入力待ち」にまとめる。

## 画面

右ペインは上から次の 7 段を並べる。
上の段ほど横目で読む情報で、下の段ほどじっくり読む情報である。
段の高さが足りないときは、目次の一覧だけがスクロールし、上の 6 段は動かさない。

### 1. 状態の灯

1 行で、いまの状態と、動いているものの数を出す。

| 状態 | 見出し | 右の小さな字 | 色 |
|---|---|---|---|
| 主線が作業中で、サブエージェントが動いていない | 作業中 | ターン n・m 手目 | 杏 |
| サブエージェントが 1 本以上動いている | n 本動いている | 指揮役も手を動かしている、失敗 k、済 j | 杏 |
| 質問を待っている（`activity.question` がある） | あなたの答え待ち | 問いの先頭 | 赤 |
| そのほかの入力待ち | 入力待ち | 最後の手 | 赤 |
| 休み | 休み | 最後の手からの経過 | 灰 |

色は端末の縁の灯と同じ語彙を使う（作業中は杏、入力待ちは赤、休みは灯さない）。

### 2. 意図

セッションが `set_turn_intent` で書いた 1〜2 文を、紫の帯に引用符つきで出す。
帯の下に「Claude いわく・書いた時刻・その後 n 手」を添える。
n は、書いてから主線とサブエージェントを合わせて呼んだツールの数である。
n が 30 を超えたら帯を薄くする（試作の I1）。
意図は矛盾を検出できないので、鮮度だけを正直に出す。

意図の出し方は次の 3 通りである。

- 今のターン（最後の利用者の指示より後）に書かれた意図があれば、その最新を出す。
- 今のターンにはまだ無く、前のターンの意図があれば、「このターンの意図はまだ書かれていない」と出し、前の意図は出さない。
- 一度も書かれていなければ、「意図は書かれていない」と出す。hangar の外で起動して取り込んだセッションは指示の注入が届かないので、いつもこの表示になる。

引用符を付けるのは、隣に確かめる事実が無い自己申告だけである。
手の説明（description）も Claude が書いたものだが、押せばコマンドと結果が隣にあり、1 手ごとに書かれて古くならないので、引用符を付けない。

### 3. 指揮役の手

主線が今のターンで呼んだツールのうち、最後の 4 手を 1 行ずつ出す。
行の文は次の規則で作る。

| ツール | 文 |
|---|---|
| Bash | `input.description`。無ければコマンドの 1 行目を等幅で |
| Read | 「読んだ：<ファイル名>」 |
| Edit、Write、NotebookEdit | 「<ファイル名> を書き換えた」「<ファイル名> を書いた」 |
| Grep、Glob | 「探した：<パターン>」 |
| Agent | 出さない（4 段目のサブエージェントに回す） |
| そのほか | ツール名と、今の `summary` |

続けて読んだ手（Read と、種類が「読む」の Bash）は 1 行に畳み、「読んだ：<最初のファイル名> ほか n 件」とする。
結果（`tool_result`）がまだ来ていない最後の手を「いま」として杏色の点で示し、`isError` の手には ✕ を付ける。
行の右端には時刻を出す。

### 4. サブエージェント

今のターンで起こしたサブエージェントと、前のターンから動き続けているものを 1 本 1 行で並べる。
行は、灯、題名、経過、最後の手の 4 つから成る。

- 題名は、起こした Agent 呼び出しの `input.description` である。
- 最後の手は、そのサブエージェントの transcript で最後に呼んだツールの文（3 段目と同じ規則）である。
- 終わったサブエージェントは、最後の手の代わりに、その本が最後に書いた本文の 1 行目を引用符つきで出す（自己申告なので）。
- 経過は、最初の手から最後の手まで（動いていれば今まで）の時間である。

並べる順は、失敗、動いている、済みの順である。
失敗とは、Agent の結果が `isError` で返ったものに限る。
レビューの「不合格」のように本文の中身で決まる結末は、赤にせず、引用した 1 行目で伝える。
試作の再生では不合格を赤にしたが、これは本文を読んで手で付けた色で、決まった規則では出せない。

見える行は 6 本までにする。
それを超えたら、動いているものと失敗を優先して並べ、済みは「済 n」のチップに畳む。
行を押すと、今の `transcript.selectAgent` でその本の transcript を開く。

### 5. 触っている層

触ったファイルを、作業ディレクトリからの相対パスの最初の区切りで束ね、最大 8 枚のタイルに並べる。
`packages/` と `apps/` の下は 2 段目まで使う（`packages/server` など）。
作業ディレクトリの外のパス（`~/.claude` など）は数えない。
agent-hangar 専用の分け方にはせず、どのリポジトリでも同じ規則で束ねる。

タイルは、書いた層を濃く、読んだだけの層を薄く、いま動いている手が触っている層を杏の縁で示す。
タイルの中の字は、層の名前と「書く n」または「読む n」である。
並べる順は手の数の多い順で、8 枚を超えた分は出さない。

材料は Read、Edit、Write、NotebookEdit、Grep、Glob のパスである。
Bash はパスを持たないので、コマンドの中の語のうち、作業ディレクトリの直下に実在する名前で始まるものだけを数える。
推測で層を当てはめることはしない。

### 6. 作業の居場所

作業ツリー、コミット、push、main の 4 つの駅を線路で結び、どこまで来たかを示す（試作の W1）。

| 駅 | 灯る条件 |
|---|---|
| 変更あり | `git status --porcelain` に行がある |
| コミット | 上流に無いコミットが 1 つ以上ある（`rev-list --count @{u}..HEAD`） |
| push | 上流に無いコミットが 0 で、作業ツリーのコミットが上流にある |
| main | HEAD が既定の枝（`origin/HEAD`、無ければ `main`、`master`）に含まれる |

上流が無い枝は、push の駅に「上流なし」と出す。
作業ディレクトリが git でなければ、この段ごと出さない。

git は読むだけで、書く操作は呼ばない。
Claude が同じ作業ツリーで git を使っているので、ロックを奪い合わないよう `GIT_OPTIONAL_LOCKS=0` を付けて呼ぶ。
呼ぶのは、右ペインが開いていてセッションが動いている間の 15 秒ごとと、種類が「コミット」の手が来た直後だけである。
1 回の呼び出しは 2 秒で打ち切り、失敗したらこの段を「読めなかった」と出す。

### 7. 目次

今の目次をそのまま残す（押すとそのターンを開き、左の Claude もその指示へ跳ぶ）。
行の下に、そのターンの手の種類を 1 手 1 升の細い色帯で並べる（最新の 40 手まで）。
「読んでばかり」「書いては落ちて」が、数字より速く形で分かる。

## 手の種類

色帯とタイルに使う手の種類は、ツール名とコマンドの頭の語から決める。
規則は `packages/shared` に置き、サーバと UI の両方が同じものを使う。

| 種類 | 色 | 当てはまるもの |
|---|---|---|
| 読む | 灰 | Read、Grep、Glob、WebFetch、WebSearch。Bash の `cat`、`head`、`tail`、`ls`、`grep`、`rg`、`find`、`jq`、`wc`、`sed -n`、`git status`、`git log`、`git diff`、`git show` |
| 書く | 藍 | Edit、Write、NotebookEdit。Bash の `sed -i`、`tee`、`mkdir`、`cp`、`mv` |
| 走らせる | 杏 | Bash の `npm`、`npx`、`vitest`、`tsc`、`node`、`cargo`、`pytest`、`make` |
| コミット | 緑 | Bash の `git commit`、`git merge`、`git push`、`git rebase`、`git cherry-pick` |
| 失敗 | 赤 | 種類によらず、結果が `isError` のもの |
| その他 | 薄い灰 | どれにも当てはまらないもの |

決めきれないものは「その他」にし、無理に当てはめない。
コマンドの頭の語は、`cd <dir> &&` と環境変数の代入を読み飛ばしてから取る。

## 材料とサーバの仕事

### ライブの要約

サーバは `GET /api/sessions/:id/live` で、次の形の要約を返す。

```ts
type LiveDigest = {
  sessionId: string;
  turnStartSeq: number | null;        // 今のターンの頭（最後の利用者の指示）
  intent: { text: string; at: number; stepsSince: number; inThisTurn: boolean } | null;
  agents: Array<{
    agentId: string;
    title: string;                     // Agent 呼び出しの description
    state: 'running' | 'done' | 'error';
    startedAt: number; lastAt: number;
    last: { text: string; kind: StepKind; isError: boolean } | null;
    report: string | null;             // 終わった本の最後の本文の 1 行目
  }>;
  layers: Array<{ name: string; read: number; wrote: number; now: boolean }>;
  where: { dirty: boolean; ahead: number | null; upstream: boolean; inDefault: boolean } | { error: string } | null;
};
```

指揮役の手と目次の色帯は、UI がすでに読み込んでいる主線のイベントから presenter が作る。
今の目次も主線のイベントから UI で作っているので、同じ場所に足す。
サブエージェント、意図、層、居場所は、主線とサブエージェントを同時に読まないと作れないか、git を呼ぶので、サーバが作る。

要約は、今のターンの頭から読む。
大きいセッション（本文が 60 MB を超えるものがある）でも先頭から全部は読まない。
セッションごとに最後に読んだ位置を覚えておき、追記の分だけ読み足す。

### サブエージェントの結び付け

Agent 呼び出しとサブエージェントの transcript は、結果の記録にある `toolUseResult.agentId` で結ぶ。
実物で確かめると、バックグラウンドで起こした Agent の結果は `status: 'async_launched'` と `agentId` を持っていた。
今の presenter は「N 番目の Agent 呼び出しが時刻順で N 番目の id」という位置の突き合わせをしている。
`agentId` が取れない古い記録に限って、この突き合わせに落とす。

終わったかどうかは次の順で決める。

- バックグラウンドで起こしたものは、主線に届く `<task-notification>` の `<task-id>` と `<status>` で決める。
- 前面で起こしたものは、Agent の結果が `async_launched` でない形で返った時点で終わりとする。
- 結果が `isError` なら失敗とする。

### 更新の流れ

今は transcript が伸びると、サーバが `transcript.appended` を WS で配っている。
サブエージェントのファイルが伸びたときも、同じ親のセッション ID で飛ぶ。
UI は、開いている画面のセッションについてこれを受けたら、`/live` を取り直す。
取り直しは 1 秒に 1 回までにまとめる。

## MCP と指示の注入

### set_turn_intent

新しい MCP ツール `set_turn_intent({ session_id?, text })` を足す。
`text` は空白を除いて 1 字以上 200 字以下で、範囲の外なら断る。
セッション別の URL では `session_id` を省けて、ほかのセッションを指せない（今の `set_session_summary` と同じ）。
ツールの説明文には、今のツールと同じく「agent-hangar」を含める。

意図は端末ローカルの新しいテーブルに積む（マイグレーション version 12）。

```sql
create table turn_intents (
  session_id text not null,
  at integer not null,
  text text not null,
  primary key (session_id, at)
);
```

共有テーブルにしないのは、意図がそのターンのあいだしか意味を持たず、同期すると D1 の書き込みの枠（月 5 ドルの上限）を使うからである。
`set_session_summary` とは別のツールにする。
要約はセッション全体の粒度で、ターンの意図とは粒度が違い、同じツールに混ぜると、毎手書くか一度も書かないかに割れやすい。

### 注入する指示

`renderInjection` の本文に次の 2 行を足す。

```
ターンを始めたときと方針を変えたときは、set_turn_intent に、このターンで何のために何をするかを 1〜2 文で書いてください。
Bash と Agent の description は日本語で 20 字以内にしてください。
```

2 行目は、主線の Bash と Agent の説明を日本語にするためのものである。
実物では、日本語で会話しているセッションでも description は英語だった。
サブエージェントには `--append-system-prompt` が届かないので、サブエージェントの手の説明は英語のまま残ることがある。
hangar は `CLAUDE.md` を書かない（設計書の原則「読み取り専用」）ので、ここは受け入れる。

## 作る順番

1. 状態の灯、意図（MCP、テーブル、注入を含む）、指揮役の手、サブエージェント、目次の色帯。手の種類の規則と `/live` の骨組みもここで入れる。
2. 触っている層と作業の居場所（git を読むサーバの機能を含む）。
3. 用語の解説。手の文と意図の中の語を押すと、説明器がペルソナに合わせて短く解説する。ペルソナの作り方（hangar の索引から作る）はこの回で決める。

1 回目が済んだら、利用者に実物で数日使ってもらい、2 回目の前に見直す。

## 確かめ方

- 手の種類の規則は、実物の transcript から抜いた Bash のコマンドの表で単体テストする。
- `/live` の要約は、実物から切り出した主線とサブエージェントの jsonl を材料にして、サーバのテストで確かめる。
  材料には、バックグラウンドの Agent、前面の Agent、`isError` の Agent、`agentId` の無い古い記録を含める。
- git の居場所は、一時ディレクトリに作ったリポジトリで 4 つの駅と「上流なし」「git でない」を確かめる。
- 画面は testing-library で、段ごとの表示と、6 本を超えたときの畳み方と、意図の 3 通りの出し方を確かめる。
- 最後に `.app` をビルドし、hangar から起動したセッションでサブエージェントを走らせ、手元の Chrome で実物の画面を撮って確かめる。

## まだ決めていないこと

- 意図の帯を薄くする閾値（30 手）は試作の値で、使ってみて見直す。
- 用語の解説の説明器とペルソナ（3 回目）。
- 目次の色帯を過去のターンにも出すか。UI が読み込んでいない古いターンは色帯が作れないので、1 回目は読み込んだターンだけに出す。
