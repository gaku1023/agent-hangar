# 「この PC で再開」を、ほかの PC から引き継ぐ操作にする

2026-10-16。利用者との相談で決めた分と、作り手に任せる分を書く。

**実装のあとで変わったこと（正本は `docs/design.md`）。**
同期の版 6（#276）が先に main に入り、heartbeat を共有しなくなったので、相手が作業中かどうかの判定（`runs.live_status`）はやめ、確認の 1 枚の帯を 1 つにした（利用者の決定）。
互換の版は上げず、引き継ぎの 2 つの表は版 6 の中に足した。
画面の文言は、アプリの用語集の試験に合わせて「止め」を「停止」、「動いている」を「実行中」などに替えた。

## 意図

ほかの PC で動いている会話は、今はロックされていて「この PC で再開」を押せない。
押せるのは、相手の生存確認（heartbeat）が 2 分途絶えて `stale` になったときだけである（`docs/design.md` の「他端末セッションのロックと『この PC で再開』」）。

困るのは、手元にこの PC しか無いときに、もう 1 台で会話を開きっぱなしにしている場面である。

- 相手の Hangar が起きていると、heartbeat が出続けるので、いつまでも押せない。
- 相手の Hangar を終了しても、tmux（Windows は psmux）の中の claude は生き残る。2 分たてば押せるが、相手の claude は残ったままで、あとで本文を伸ばしうる。

ほかの PC で動いている会話を、この PC から**止めて引き継げる**ようにする。

## 目標

- 相手の Hangar が起きていれば、相手に止めてもらい、相手の最後の本文を降ろしてから再開する。会話は枝分かれしない。
- 相手が聞ける状態になければ（Hangar が止まっている、応答しない）、確認のうえこちらで引き継ぐ。
- 引き継がれた側では、次に Hangar が動いたときに、その会話の claude を止める。
- 引き継がれた側の画面で、どの PC に引き継がれたかが分かる。

## 目標にしないもの

- プロジェクトのファイル、未コミットの変更、開発環境の受け渡し（今までどおり同期しない）。
- 相手の作業中のターンを終わりまで待つこと。
- ふだんの同期の間隔を縮めること。

## 失敗とみなすもの

- 引き継いだあとも、相手の claude が黙って動き続け、本文を伸ばし続けること。
- 無料枠の使用量が目に見えて増えること。
- 古い版の PC が同期から締め出されること。

## 決めたこと（利用者）

1. **案 C。** 相手の heartbeat が新しければ（`stale` でなければ）、クラウド経由で「止めて」と頼み、「<相手の PC> を止めています…」を出して待つ。相手が止まって最後の本文が届いたら、降ろして再開する。90 秒たっても返事がなければ、「応答がありません。このまま引き継ぎますか（向こうで書かれた分は枝分かれします）」と聞いて、承諾したら引き継ぐ。heartbeat がすでに `stale` なら、待たずにすぐ引き継ぐ。
2. **相手が作業中のときは、すぐ止める。** 確認の 1 枚に「<相手の PC> は作業中です。止めるとそのターンは途中で切れます」と書き、承諾したら止める。ターンの終わりは待たない。利用者が自分で奪うと決めた操作だからである。
3. 見積もりは「1 回の引き継ぎで D1 書き込み約 30 行、読み取り約 100」で了承済み。

## 画面（利用者が試作から選んだ、2026-10-16）

試作は hangar-explainers の force-resume-2026-10-16（リポジトリの外）。

- **A1 確認の 1 枚。** 今の 1 枚（前の PC → この PC のカード、同期されないものの黄の帯）はそのまま。上に赤みの帯を 1 本足す。アイドル・入力待ちなら「<相手> で実行中です／引き継ぐと、<相手> の claude を止めてから、この PC で再開します。」、作業中なら「<相手> で作業中です／止めるとそのターンは途中で切れます。そのあと、この PC で再開します。」。題は「ほかの PC で動いている会話を、この PC で引き継ぎますか」、ボタンは「止めて引き継ぐ」。
- **B1 待っている間。** 押した 1 枚がそのまま進み具合に変わる。題は「<相手> から引き継いでいます」（回る印）。段は 4 つ：止めるよう頼みました／<相手> が止まるのを待っています（経過秒）／最後のトランスクリプトを受け取る／この PC で再開する。90 秒の目安を細い線で出し、「<相手> の Hangar がクラウドを見に来るまで、最大 30 秒ほどかかります。」を添える。ボタンは「取り消す」だけ。
- **C2 返事がないとき。** 同じ 1 枚が警告に変わる。題「<相手> から返事がありません」、文「<相手> の Hangar が閉じているか、ネットにつながっていない可能性があります。」、黄の帯「このまま引き継ぐと、会話が分かれることがあります／<相手> の claude はまだ動いている可能性があります。そちらで続きが書かれると、その分はこの PC の会話に入りません。claude は、次に <相手> で Hangar が動いたときに止まります。」。ボタンは「取り消す」「もう少し待つ」（もう 90 秒待つ）「このまま引き継ぐ」の 3 つ。押した時点で相手がもう `stale` のときは、待たずに前の PC とこの PC のカードつきの 1 枚（題「<相手> が応答していません。この PC で引き継ぎますか」、前の PC のカードに「最後の応答：N 分前」）を出し、ボタンは「キャンセル」「このまま引き継ぐ」。
- **D1 引き継がれた側。** 会話の見出しの下に灰色の 1 行「<この PC> に引き継がれました（時刻）。いまは <この PC> で動いています。」。端末の終わりにも 1 行「[hangar] <この PC> に引き継がれたため、この PC の claude を止めました。」。知らせの札は出さない。一覧の行は今までどおり「<この PC> で実行中」。

## 制約

- 頼みの到達は、相手の pull の周期（30 秒、`sync/engine.ts` の `PULL_INTERVAL_MS`）で決まる。相手の周期は縮めない。待つ側だけ、待っている間は短い間隔（5 秒ほど）で取りに行ってよい。
- `runs` の行は持ち主の PC が 30 秒ごとに行全体で書き直す（heartbeat）。依頼側がほかの PC の `runs` の行に列を足して書くと、後勝ちで消える。頼みは別の共有表で運ぶ。
- Worker は `SHARED_TABLES` に無い表を含む push を丸ごと 400 で断る。新しい表は Worker の配備と互換の版（`COMPAT_VERSION` 5→6）を伴う。`config_snapshots` の先例にならい、Worker の版が届くまでその表の行を書かない。Worker の下限（`MIN_DEVICE_COMPAT`）は上げない。古い版の PC には頼みが届かず、90 秒で打ち切る経路に落ちる。殻（`health.rs`）の版も同時に上げる。
- 今の `resumeHere`（`sync/resumeHere.ts`）は、サーバ側でロックを見ていない（画面で押せなくしているだけ）。引き継ぎの処理は手元の Hangar のサーバ（Node）に作り、そこでロックと heartbeat を見直す。Worker は表の受け口のままで、奪い合いの排他は持たせない（作り手の判断）。
- 相手を止めるのは既存の `RunManager.kill`（tmux のセッションごと落とす）。止めたあと、run の終わりの flush（`sync/flushOnRunEnd.ts`、直後と 5 秒後）で本文が上がる。待つ側は、相手の run が終わり、最後の本文が台帳（`files`）に載って手元に降りたことを確かめてから写す。
- 実物のクラウドに触る確かめ（Worker の配備、2 台をまたぐ確かめ）は、その都度利用者に聞く。
- 公開リポジトリなので、試験や文書に実際の PC 名や利用の実数を書かない。

## 流れ（決めた形）

**依頼側（この PC）**

1. 「この PC で再開」を押すと、今の確認の 1 枚を出す。相手が生きたロックを持っていれば、ボタンを押せるようにし、1 枚に「<相手の PC> で実行中です。止めて引き継ぎます」を添える。作業中なら決めたこと 2 の文を添える。
2. 承諾したら、相手が `stale` でなければ頼みを書き、待つ。画面は「<相手の PC> を止めています…」（取り消しできる）。
3. 相手の run が終わり、最後の本文が降りたら、今の「この PC で再開」の流れ（写す → `claude -r`）に入る。
4. 90 秒で返事がなければ、決めたこと 1 の確認を出す。承諾で引き継ぎ、断ったら頼みを取り下げて元に戻る。
5. 相手がすでに `stale` なら、2〜4 を飛ばして引き継ぐ。

**引き継がれる側（ほかの PC）**

1. pull で自分の run あての頼みを見つけたら、その run を `kill` で止める。止めた理由（例 `end_reason = 'taken-over'`）を残す。
2. 最後の本文を上げてから、頼みに応答を書く。
3. 起動時（`recoverAtStartup`）と見回り（`tick`）で、引き継がれた会話の claude が tmux に残っていれば止める。依頼側の新しい run が先にあれば、手元の古い run は生き返らせない。
4. 画面には「<この PC> に引き継がれました」を出す（会話の見出しの下と、知らせ）。

## 作り手に任せること

- 新しい共有表の名前と列（依頼の id、会話、相手の run、依頼した PC、依頼の時刻、応答の時刻と結果、取り下げ）。主キーは依頼の id がよい。
- 待つ側の取りに行く間隔の細部と、打ち切りの 90 秒を定数にするか。
- 頼みの行を消す時期（応答から一定時間後など）。
- 画面の文言と配置。開発の流れどおり、作る前にブラウザで開ける試作を出し、利用者に選んでもらう（確認の 1 枚、待っている間、打ち切りの確認、引き継がれた側の表示）。
- `docs/design.md` の該当の節（ロックの節、互換の版の節）の書き直し。

## 作り手が決めた細部

- 相手が互換の版 5 以下（新しい表を知らない）とき、頼みは書いて 90 秒待つ。届かないだけで、仕様の流れは変わらない。
- 「作業中」の判定は、既存の run の状態（作業中、入力待ち、アイドル）を使う。
- 最後の本文が降りたことは、応答の行に相手が上げた最後の本文の版（sha256 と大きさ）を載せ、手元の台帳と突き合わせて確かめる。
- 同じ会話に複数の PC が同時に頼んだときは、先に応答を得た方が引き継ぐ。後の方は、相手の run がもう終わっているので、ふつうの「この PC で再開」（手元の本文が古ければ今の上書きの確認）に落ちる。
