# 段 3 UI の骨格

作り替えの全体計画（`2026-10-07-refactor-roadmap-design.md`）の段 3 である。
画面を 1 枚作り替えるときに触る場所を「Presenter、View、表の 1 行」まで減らし、文言を日英の辞書から出せるようにする。
画面に見える振る舞いは変えない。
辞書の中身（日本語と英語の語）を埋めるのは段 4 である。

調査（2026-10-09、main `b8faedd`）で、いまの骨格の問題を次のように数えた。数は各 PR で数え直す。

- 同じ事実を State と Store の 2 か所に持っている項目が 5 つある。同期の状態と未送信の数、索引の段階、要約の失敗、作業フォルダの一覧と選んだフォルダ、通知の許可である。
- Store から分かる事実を、Runtime がイベントにして Mediator へ往復させている経路が 5 種ある（`waiting.changed`、`live.changed`、`return.due`、`split.resolved`、`waiting.resolved`）。このほか、State が同期の状態を二重に持つせいで、HTTP の応答と起動時の読み込みをサーバのイベントに見せかけて流す所が 4 か所ある。
- Intent 106 種のうち 32 種は、状態を変えずに API を 1 回呼ぶだけである。それでも Intent と Effect の 2 つの定義を持ち、Effect は 111 種ある。
- 保存しない一時の状態が State に 6 つある（開いているターン、ターンへの跳び先、本文の検索、跳び先、一覧のページ、節の開閉）。
- 日本語の文字列を直に見ている試験は 79 ファイル、1,937 行ある。

## 骨格の方針

次の 3 つを行う。

1. Mediator が Store を読めるようにする（`transition(state, store, input)`）。往復の 5 種は Mediator の中の派生に替え、二重に持っている 5 項目は Store だけに置く。
2. API を 1 回呼ぶだけの Intent 32 種は、Effect を挟まずに「Intent から API の呼び出しへ」の表で引く。
3. 一時の状態のうち、Presenter と Mediator のほかの領域が読まないものを View へ下ろす。実装で確かめると、当てはまるのは本文の検索の 1 つだけだった。開いているターン、ターンへの跳び先、跳び先、一覧のページ、節の開閉は、Presenter か Mediator が読むので State に残す。

退けた案は 2 つある。
1 だけを行う案は、Intent と Effect の二重の定義を残すので、段 4 で画面を作り替えるたびに 2 か所を触ることになる。
Store と State を 1 つにまとめる案は、段 2 のあとでは Store がサーバのイベントを当てる 1 本に縮むので得る物が小さく、段 4 を待たせる。

## 文言の辞書

- **置き場**：鍵の型と、日本語と英語の 2 つの辞書を shared に置き、UI とサーバが同じ関数 `t()` で引く。全体計画の D5 が範囲とする 3 つ（画面、画面に出るサーバの文、Claude に渡す注入の文）を、1 つの仕組みで満たすためである。辞書を UI だけに置き、サーバは符号と引数を返す案は、注入の文を別の仕組みで訳すことになるので採らない。
- **鍵**：`画面.部品.意味` の形にする（例：`session.kill.confirm`）。辞書は `Record<Key, string>` とし、鍵の抜けと余りを型で止める。引数は `{n}` の置き換えで渡す。
- **言語の設定**：この PC の設定のファイル（`SettingsDto.language: 'ja' | 'en'`）に置く。設定の実体はこのファイルで、DB の表 `settings_local` は使われていなかった。サーバも読めるので、注入の文と MCP の文が画面の言語にそろう。ブラウザの保存領域に置く案は、サーバが言語を知らないので採らない。
- **試験**：日本語の文字列を直に見ている試験は、日本語の辞書で走らせて、書き換えない。鍵で見るのは、同じ語を別の意味に使わないことを確かめる用語の試験だけにする。
- **状態の札**：セッションとプロジェクトの状態の札（Active、Paused、Done、Archived）は、日本語でも英語のまま出す（2026-10-09 の利用者の決定）。文とボタンは、ふつうのソフトの語にする。語そのものは段 4 の用語集で決める。

この段で入れるのは仕組みまでである。
画面の文を鍵へ置き換える作業は、段 4 で画面を 1 枚ずつ作り替えるときに行う。

## 試験と設計書の整理

- CSS の試験（16 ファイル、152 本）を、禁則の 3 本だけにする。字の太さ、ガラスの質感を使ってよい場所、トークンの直書きである。
- `docs/design.md` から Intent の一覧、State の一覧、遷移の表を落とし、「型が正である」と 1 行で書く。設計書は意図と決定の記録に絞る。

## PR の割り方

各 PR は単独で動き、main に入れたあとアプリを入れ替えられる。

| # | 中身 | 前提 |
| --- | --- | --- |
| 1 | `transition` に Store を渡す（動作は変えない） | なし |
| 2 | 往復の 5 種を消す | 1 |
| 3 | 二重の 5 項目を Store へ移し、見せかけのイベント 4 か所を消す | 1、段 1 の PR 5 と PR 6（同期の表示の同じファイルを触る） |
| 4 | API を 1 回呼ぶだけの Intent を表へ | 2（同じ Mediator を触るので順に） |
| 5 | 本文の検索の状態を View へ | 1 |
| 6 | 辞書の仕組み（shared の鍵と `t()`、言語の設定） | なし |
| 7 | サーバの文と注入の文を辞書から出す | 6、段 2 の経路の分割 |
| 8 | CSS の試験を 3 本に | なし |
| 9 | design.md の一覧を落とす | なし |

6、8、9 は、段 1 と段 2 のどの PR ともぶつからないので、先に進める。
1、2、4、5 は段 2 を待たない。
3 は段 1 の PR 5 と PR 6 のあと、7 は段 2 の経路の分割のあとである。

## 範囲外

- 画面の構成と言葉、辞書の中身（段 4）。
- Store と State の統合。
- shared に残った `steps`、`intent`、`route` を UI へ移すこと。サーバが型（`LaunchParams` など）を使っているので、契約の型を切り出してからになる。段 3 の PR 4 で Intent の定義を触るときに、あわせて行えるかを見る。

## 終わりの条件

- 往復のイベントと見せかけのイベントが無い。
- 同じ事実を State と Store の両方に持っていない。
- 新しい文言を辞書の鍵で書け、言語を設定で切り替えられる。
