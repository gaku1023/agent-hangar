# クラウド同期の使い方と割り切り

README の「[クラウド同期](../README.md#クラウド同期上級者向けのベータ)」の節に書ききれない、使い方の細部と、割り切りと実測の記録です。
同期の仕組みは `docs/design.md` の「クラウド同期」にあります。

## 0.9.0 で変わったこと

0.9.0 で、クラウド同期を作り直しました。

- 参加トークンと、その中の参加用のシークレットを廃止しました。
  PC の追加は、参加済みの PC が発行する参加コード（5 分、1 回限り）と、その PC での承認で行います。
- D1 と R2 に置くもの（セッションの題、要約、TODO、ノート、ファイルのパス、PC の名前）は、PC どうしの間で暗号化してから置きます。
  Cloudflare に平文で見えるのは、鍵名、連番、時刻、端末の ID、暗号鍵の世代の番号、大きさだけです。
- 暗号鍵は人に見せない乱数で、参加済みの PC が新しい PC の公開鍵に封じて渡します。
  すべての PC を失ったときのために、setup でリカバリーキーを 1 度だけ表示します。
- `hangar setup cloud --rotate-secret` を消しました。
  PC を締め出すときは、その PC を解除します。
  解除すると暗号鍵を再生成して残りの PC に配るので、R2 の既存のファイルを読めなくすることなく締め出せます。
- PC の一覧の IP と所在地（「最後の IP」と「おおよその場所」）の表示をやめました。
  Worker も IP と所在地を保存しません。
- 0.9.0 は 0.8.x までのクラウドと同期できません。
  移行の道は無く、下の手順でクラウドを作り直します。

## 0.9.0 への作り直し

0.9.0 の PC は 0.8.x までの Worker と話せず、0.8.x の PC は 0.9.0 の Worker と話せません。
そのため、作業の順が大切です。

1. **0.8.x のうちに**、すべての PC で「今すぐ同期」を押して、旧い Worker と一度同期を済ませます。
   続けて、設定 › クラウド同期 の「Claude Code の設定の同期」のスイッチを切ります。
   作り直しの間に、どこかの PC の古い設定で `~/.claude` を上書きしないためです。
2. すべての PC を 0.9.0 に更新します。
   0.9.0 は古い形式の設定（`~/.agent-hangar/cloud.json`）では同期を始めず、設定と `hangar cloud status` に作り直しが必要なことを表示します。
3. Worker を作成した PC で、リポジトリを clone したディレクトリから `npm run hangar -- cloud teardown` を実行します。
   R2 にしか無いトランスクリプトを、他の PC の分も含めて `~/.agent-hangar/remote/` にダウンロードしてから、Worker と D1 と R2 を削除します。
   1 件でもダウンロードできなければ、何も削除せずに止まります。
4. 同じ PC で `npm run hangar -- setup cloud` を実行し、新しいクラウドを作成します。
   最後に表示されるリカバリーキーをパスワードマネージャーに保存します（下の「リカバリーキー」）。
5. 他の PC を、参加コードで参加させます（下の「PC を追加する」）。
   古い設定が残っている PC では「別のクラウドに参加しています」の警告が出るので、接続先が新しいクラウドであることを確認して「上書きして参加をリクエスト」をクリックします。
6. スマホは、PC で QR を表示して接続し直します。
7. 各 PC が、すべてのデータを新しいクラウドにアップロードします。
   共有のデータは全部の行を、トランスクリプトはクラウドを使い始めた時刻より後のものを送り直します。
   `~/.agent-hangar/remote/` にある他の PC のトランスクリプトは、作り直しから 3 日たっても元の PC が参加していなければ、受け取った PC が代わりにアップロードします。
8. 設定の同期のスイッチを入れ直します。
   適用の前に下見の一覧が出るので、上書きされる内容を確認してから適用します。

作り直しの日は、全部の行とファイルの索引の書き込みが一度に出ます。
D1 の 1 日の書き込みの無料枠を超えると、次の UTC の 0 時まで同期が止まり、日が変わると自動で再開します。
共有のデータやトランスクリプトが多いときは、PC ごとに日を分けて参加させると、1 日の量を抑えられます。

## PC を追加する（参加コード）

1. 参加済みの PC で、設定 › クラウド同期 の「PC を追加」をクリックします。
   参加コード（`XXXX-XXXX` の 8 文字）と接続先の URL が表示されます。
2. 新しい PC で、設定 › クラウド同期 の「参加コードで参加」をクリックし、接続先の URL を入力して「次へ」をクリックします。
   接続先のホスト名と、参加済みの PC の台数が表示されます（PC の名前は暗号化してあるので、承認の前は表示できません）。
3. 参加コードを入力して「参加をリクエスト」をクリックします。
   新しい PC に 6 桁の確認コードが表示されます。
4. 参加コードを発行した PC に、参加リクエストの通知が表示されます。
   新しい PC の名前と OS、確認コードを見て、新しい PC の確認コードと同じなら「承認」をクリックします。
5. 新しい PC は数秒で参加を完了し、アプリを再起動して同期を始めます。

参加コードについて知っておくこと。

- 参加コードは 5 分で期限が切れ、1 回しか使えません。
  期限が切れたら、参加済みの PC で「参加コードを再発行」をクリックします。
- 承認できるのは、参加コードを発行した PC だけです。
  その PC がスリープ中か Hangar を終了していると、新しい PC には「応答がありません」と表示されます。
  発行した PC で Hangar を開き、新しい参加コードを発行してください。
- 参加コードを人に見られても、承認しなければ参加できません。
  確認コードは新しい PC の公開鍵から導くので、別の PC が同じ参加コードでリクエストを置いても、確認コードが一致しません。
  確認コードが一致しないリクエストは「拒否」してください。
- 発行は 1 台の PC につき 10 分に 5 回までです。
  参加コードを当てずっぽうに試す要求は、Worker 全体で 10 分に 30 回まで数え、超えると正しいコードでも 10 分のあいだ断られます。
- ブラウザで開いた画面からは参加できません。
  ターミナルでは `hangar cloud join <接続先の URL>` で同じ手順を進められます（参加コードは標準入力で尋ねます）。

## リカバリーキー

リカバリーキーは、すべての PC を失ったときに、新しい PC でクラウドの暗号鍵を取り戻すためのものです。
中身は、見出し（`hangar リカバリーキー`）、作成日、接続先の URL、暗号鍵（4 文字ごとに `-` で区切った文字列）の 4 行です。
PC にはリカバリーキーの公開鍵だけを置き、秘密鍵は置きません。
なくした PC からリカバリーキーが漏れることはありませんが、後から表示し直すこともできません。

**setup での保存。**
`hangar setup cloud` は、最後にリカバリーキーを 1 度だけ表示します。
パスワードマネージャーに保存するか、`--save <パス>` でファイルに書きます（権限は所有者だけが読める 0600）。
`--save` を付けずにターミナルで実行すると、保存先を尋ねます。
保存したら、暗号鍵の末尾 4 文字を入力します。
合うまで setup は終わりません。
3 回表示し直しても合わなければ、名簿と暗号鍵の箱を置かずに止まります。
もう一度 `hangar setup cloud` を実行すると、新しいリカバリーキーを作り直して、表示からやり直します。
合ったら、ターミナルの画面とスクロールバックを消します。

**再発行。**
設定 › クラウド同期 の「リカバリーキーを再発行」で、新しいリカバリーキーを表示します。
120 秒たつと暗号鍵を伏せるので、それまでにコピーかファイルへの保存で控えます。
「保存しました」をクリックし、暗号鍵の末尾 4 文字を入力して「完了」をクリックすると、新しいリカバリーキーに切り替わり、古いものは使えなくなります。
末尾 4 文字を入力する前に閉じたときは、何も変わらず、古いリカバリーキーが使えるままです。
再発行は、再発行の前に取られた D1 のバックアップまでは書き換えられず、そこからは古いリカバリーキーで過去の暗号鍵を取り出せます。
古いリカバリーキーが漏れたと思われるときは、再発行に加えて、暗号鍵そのものを再生成します。
暗号鍵の再生成は PC の解除のときに行うので、PC が 2 台以上あれば、どれか 1 台を他の PC から解除し、参加コードで再参加させます。

**`hangar recover`。**
すべての PC を失ったときは、新しい PC で、リポジトリを clone したディレクトリから `npm run hangar -- recover` を実行し、リカバリーキーの 4 行を貼り付けます。
リカバリーキーは標準入力から読み、コマンドの引数には載せません。
Worker を作成した Cloudflare のアカウントで wrangler にログインしている必要があります。
Worker の名前が接続先の URL の先頭と違うときは `--name` を、アカウントが複数あるときは `--account-id` を付けます。
recover は、名簿に登録されたリカバリーキーと一致することを確かめてから、この PC を新しい PC として参加させます。
再発行の前の古いリカバリーキーは断られます。

この PC が以前このクラウドに参加していたと、「この PC の端末 ID は登録済みです」と表示して止まります。
そのときは hangar を終了し、`~/.agent-hangar/device.json` を削除してから、もう一度 `hangar recover` を実行します。
新しい端末 ID で登録し直すので、この PC で前の端末 ID のまま作ったセッションとプロジェクトの場所は、別の PC のものとして扱われます。
古い端末 ID は Worker の端末の一覧に残り、新しい PC が参加するときの「参加済みの PC の台数」に数えられ、PC の一覧には名前のわからない PC として表示されます。
その行を解除すれば、台数に数えなくなります。

## PC とスマホの解除

**他の PC の解除。**
設定 › クラウド同期 の PC の表で、その PC の行の「解除…」をクリックします。
解除すると、その PC の端末トークンを無効にし、暗号鍵を再生成して、残りの PC とリカバリーキーに配ります。
解除した PC は、解除の後に書かれたデータを復号できません。
R2 の既存のファイルは暗号化し直しません。
解除した PC は過去の暗号鍵を持っていますが、端末トークンが無効なので Worker から取得できません。
暗号鍵の再生成は動いている Hangar が行うので、ターミナルの `hangar cloud revoke <ID>` も、動いている Hangar を呼びます（Hangar が終了していると、PC の解除は断られます）。
解除した PC は、参加コードで再参加できます。

**この PC の参加の解除。**
設定 › クラウド同期 の末尾の「参加を解除…」か、`hangar cloud leave` で行います。
この PC の `cloud.json` を削除し、選べばクラウドの一覧からもこの PC を解除します。
この PC に受信済みのトランスクリプト（`~/.agent-hangar/remote/`）は削除しません。

**スマホの解除。**
設定 › クラウド同期 のスマホの表で、そのスマホの行の「解除」をクリックします。
確認はなく、右下に「元に戻す」が 5 秒表示されます。
5 秒たつと、そのスマホのトークンを無効にし、スマホ用の暗号鍵を再生成して、残りのスマホに配ります。
他のスマホの接続は切れません。
スマホのトークンは、30 日使わないと期限が切れ、使うと延長されます。
接続から 90 日たつと、使っていても接続し直しが必要です。
スマホの行には、残りの日数と再接続の日付が表示されます。

## 割り切りと限界

どれも実際に確かめたか、意図して残したものです。

1. **Cloudflare アカウントそのものは、利用者が守る前提です。**
   暗号化が守るのは、D1 と R2 の中身が漏れたとき（Cloudflare の従業員、開示の要求、障害、バックアップ）です。
   Cloudflare やアカウントを取った人が Worker を書き換える攻撃（データの隠蔽や差し戻し、暗号鍵の箱の偽造、参加リクエストやスマホの接続の公開鍵の差し替え、スマホの画面の差し替え）は守りません。
   PC の参加では、確認コードを照合すれば公開鍵の差し替えに気づけます。
   Cloudflare のアカウントには二段階認証を付けてください。
2. **無料枠の上限に達すると、次の UTC の 0 時まで同期が止まります。**
   hangar は量を数えません。
   上限に達すると Cloudflare が断るので、その失敗を見分けて止め、日が変わると自動で再開します。
   無料プランは上限を超えても課金されず、要求が断られるだけです。
   止まっている間に「今すぐ同期」を押すと、1 回だけ試し直します。
   まだ断られれば、また次の UTC の 0 時まで退いて、トーストで知らせます。
   なお R2 自身の枠は月ごとの別勘定で、この使い方（1 セッションを 1 日走らせて上げ下ろしが 2,880 回ほど）では月の上限に対して桁が 2 つ小さく、先に当たるのは必ず D1 の書き込みの側です。
3. **他端末の run は止まりません。** ロックは見せるだけです。「この PC で再開」は本文を降ろして手元で新しい run を立てるので、同じセッションの本文が 2 か所で伸びること（枝分かれ）があります。索引は 1 つのファイルだけを採るので画面は二重になりませんが、本文そのものは分かれます。
4. **`~/.agent-hangar/backups/` は直近 20 回ぶんだけ残します。**
   控えを取るのは、設定の取り込み（`claude-config/`）、「この PC で再開」での本文の上書き（`transcripts/`）、セッションの名前の競合（`memos/`）の 3 つで、どれも新しい方から 20 世代を残して古いものを消します。
   `claude-config/` は取り込みのたびに刈り、`transcripts/` と `memos/` は控えを取った後と、サーバを起こしたときに刈ります。
   この置き場の外に残る控え（プロジェクトのメモの隣の `memo.md.bak-<日時>` と、設定の同期が残す `*.conflict-*`）は消しません。
5. **孤児は掃除しますが、解除した PC の本文は消しません。**
   本文の PUT は R2、D1 の順なので、途中で倒れて残るのは索引に無い R2 の本体だけです。
   Worker は `GET /files` を契機に、6 時間に 1 回だけ R2 を 50 件と索引を 50 行まで見て、索引に無い本体と、本体の無い索引の行を消します。
   置いてから 1 時間たっていないものには触らないので、書いている最中の 1 本は消えません。
   誰も本文を降ろさない日は `GET /files` が来ないので走りませんが、孤児が増えるのも上げ下ろしをした日だけです。
   掃除自身が D1 に書くのは、孤児が数件のときの実測で 1 回 7 行、1 日 4 回で 28 行です（枠の 0.03%）。
   ゴミ箱から 30 日たったセッションの本文は、0.9.0 から PC が消します（中身が暗号化されて Worker には読めないため）。
   PC を解除しても、その PC が上げた本文と設定と行は R2 と D1 に残します。
   他の PC が一覧と検索とこの PC で再開で使っており、解除は再参加すれば戻る操作だからです。
   解除した PC の本文を明示的に消す操作は、まだありません。
6. **暗号鍵を再生成した後も、古い世代のものが一部残ります。**
   再生成の後に書き直した行は新しい名前で D1 に入り、古い名前の行は残ります（新しい方が勝つので、中身は正しく同期されます）。
   設定の同期の束も新しい名前で置き直し、古い束は R2 に残ります。
   トランスクリプトは、書き直したときに古い名前のものを消します。
   残るのは D1 の行数と R2 の保存量だけで、消す操作はまだありません。
7. **`CLAUDE_CONFIG_DIR` と `HANGAR_CLAUDE_DIR` は別物です。** 前者は起こされた `claude` が見る設定の置き場、後者は hangar が読む置き場です。普段はどちらも `~/.claude` ですが、試しの環境を分けるときは両方を向けてください（実物確認で見つかりました）。
8. **アカウントを足すと、2 つ目以降の置き場（`~/.claude-2` など）の中身は `~/.claude` へのリンクになります。** 設定・スキル・履歴は共有で、別になるのは認証（Keychain の項目と `.claude.json`）だけです。hangar はトークンを読みません。渡すのは `CLAUDE_CONFIG_DIR` だけで、ログインは `claude auth login` に任せます。リンクの場所に実ファイルがあると起動を断ります。中身を確かめて、要らなければ消してください。
9. **取り込んだ設定ファイルの更新時刻は、相手の端末で編集した時刻になります。** 手元で書いた時刻ではありません。どちらが新しいかの判定をホームをまたいで揃えるためです。
10. **確認は 1 台の Mac で 2 端末を模して行いました。**
    `HANGAR_HOME` と `HANGAR_CLAUDE_DIR` を分け、2 つのポートで起こしています。
    実際に別のマシンから接続することは、まだ確かめていません。
    孤児の掃除はこの確認より後に入れたもので、偽のクラウドとローカルの workerd（miniflare）の試験だけで確かめています。
    上限で退く処理も後に入れたもので、偽のクラウドと、手元の Worker の前に置いた中継でだけ確かめています。
    0.9.0 の作り直し（参加コード、リカバリーキー、暗号化、解除と暗号鍵の再生成）も、偽のクラウドと miniflare の試験だけで確かめています。
    実物の Cloudflare では動かしていません。
11. **降ろすのを諦めた本文は画面に出ます。**
    ヘッダーに件数が出て、Settings のクラウド同期の節に鍵と理由と試した回数が並びます。
    同じ 2 か所に、まだ上げていない本文の件数も出ます。
    30 分ごとと、サーバを起こし直したときに自動で試し直すので、放っておけば回復します。
12. **`hangar cloud teardown` に合言葉を一度に流し込むと、2 つ目が読めません。** 安全側に倒れて中止します。手で打つか、1 つずつ送ってください。
13. **参加より前の本文はクラウドに上がりません。**
    上げ始める時刻は、`hangar setup cloud`、参加、`hangar recover` が `cloud.json` を書くのと同じ時点で `~/.agent-hangar/hangar.db` の `sync_state` に 1 度だけ刻みます。
    作り直しで新しいクラウドへ移っても、この時刻は動きません。
    いま刻まれている時刻は `hangar cloud status` の「本文:」の行で確かめられます。
    上げたければ、そのセッションを再開するか `hangar cloud backfill` を実行してください。
14. **マイグレーションの版 8 が走ります。** `transcript_files` に `device_id` の列が増え、R2 との同期の台帳である `file_sync` が出来ます。索引の作り直しは起きません。
15. **1 台目の初回の設定は、途中で止まることがあります。**
    止まったら、原因を直してから `npm run hangar -- setup cloud` をもう一度打ってかまいません。
    作成済みの D1 と R2 は、そのまま使います。
    よく止まるのは次の 2 つです。
    - R2 が有効になっていない。
      Cloudflare のダッシュボードで R2 を有効にします（支払い方法の登録が要ります）。
    - `workers.dev` のサブドメインが未登録。
      ダッシュボードの Workers & Pages でサブドメインを決めます。
      Worker の URL に出るので、メールアドレスや本名とつながらない名前にしてください。
      あとで変えると、接続先の URL と、リカバリーキーの URL の行が変わります。
16. **Cloudflare のアカウントが複数あるときは、作る先を自分で選びます。**
    `--account-id <ID>` か環境変数 `CLOUDFLARE_ACCOUNT_ID` で指定します。
    他の人も入っているアカウントに作ると、その人たちが Worker を書き換えられます（1 の守らない攻撃に当たります）。
17. **clone の版は、アプリと同じ版のタグにしてください。**
    clone の CLI は `~/.agent-hangar/hangar.db` をマイグレーションしながら開きます。
    互換の版はクラウドと話せるかどうかだけを決めるもので、手元の DB は守りません。
    アプリより新しい版で打つと、アプリより先に DB が進んでしまうおそれがあります。
18. **`npm ci` のとき、npm 11 が install scripts の警告を出すことがあります。**
    `better-sqlite3`、`esbuild`、`node-pty`、`workerd` などについての警告で、無視してかまいません。
19. **設定が済んだら、アプリを終了して開き直してください。**
    サーバは `cloud.json` を起動時に 1 度だけ読むので、開き直すまで同期は始まりません。
    1 台目も同じです。
    アプリから参加したときは、アプリが自動で再起動します。
20. **スマホは PC の暗号鍵を持たず、スマホ用の暗号鍵と使い捨ての券で接続します。**
    QR に入っているのは、接続先の URL、5 分で失効して 1 回しか使えない券、PC の名前、期限だけで、暗号鍵は入っていません。
    スマホは自分の鍵ペアを作り、QR を表示している PC が、スマホ用の暗号鍵をスマホの公開鍵に封じて渡します。
    スマホ用の暗号鍵は、受信箱、起動の依頼、`@` と `/` の問い合わせ、画像の暗号にだけ使い、PC どうしの暗号鍵とは別です。
    スマホや QR が漏れても、PC として参加することも、R2 の本文を読むこともできません。
21. **スマホからは、承諾なしで、選んだ権限モードの会話を、どの PC にも起こせます。**
    PC 側に上限や確認はありません。
    スマホを手にした人は、受信箱（待っている内容、会話の題、意図の文）を読め、全部の PC に権限モード込みで会話を起こせます。
    なくしたらすぐ、設定 › クラウド同期 のスマホの表から解除してください（上の「スマホの解除」）。
    解除すると、そのスマホのトークンは通らなくなり、スマホ用の暗号鍵も再生成されるので、解除したスマホは解除の後の受信箱を読めません。
22. **Worker が配るスマホの画面は、Cloudflare のアカウントを取られると差し替えられます。**
    受信箱の暗号は、鍵を持つスマホの画面の中で解きます。
    その画面は Worker が配るので、Cloudflare のアカウントを取った人は、配る画面を書き換えて、スマホ用の暗号鍵で受信箱を読み、会話を起こせます。
    CSP（`default-src 'self'` ほか）は、画面が外へ送ることと、外のスクリプトを読むことを防ぎますが、配る側を取られた場合は守れません（1 の守らない攻撃に当たります）。
23. **スマホからの起動は、PC が pull したときに受け取ります。**
    PC の pull は 30 秒ごとなので、会話が始まるまで最大で 75 秒ほどかかり、それを過ぎた依頼は起こされません。
    呼び鈴（26）がつながっている PC は、依頼を置いた直後に鳴らされてすぐ pull します。
    受け取った後に PC の応答が失われたときは、起こさずに時間切れとして終わります（二度起こさないための側に倒しています）。
24. **スマホの画面に会話の中身は出ません。**
    会話を開いて続けるのは、Claude の Remote Control です。
    API キーのアカウントでは `--remote-control` を付けずに起こすので、起こせても Remote Control では開けません。
25. **スマホで確かめたのは、手元の偽のクラウドと miniflare までです。**
    実際の Cloudflare、実際の iPhone や Android、実際の Remote Control の通しでは、まだ動かしていません。
    呼び鈴（Durable Object）と画像（R2）も、実物では未確認です。
    未確認なのは、Durable Object の配備（`migrations`）、PC の WebSocket が数時間つながり続けるか（Cloudflare 側の切断の頻度）、`setWebSocketAutoResponse` の `ping` がリクエストに数えられないこと、R2 の一覧と置く操作の振る舞い、iPhone のホーム画面のアプリでのカメラ（QR と撮影）と写真の選択、Windows の PC からの呼び鈴です。
26. **呼び鈴（Durable Object）は、PC から Worker へつなぎっぱなしにします。**
    PC は、スマホを 1 台以上つないでいて、Worker の版が 8 以上のときだけつなぎます。
    つないでいる間は 30 秒ごとに `ping` を送り、Durable Object は眠ったまま自動で `pong` を返します。
    Cloudflare 側の切断や Worker の再配備のたびに、PC はつなぎ直し、そのつど Durable Object のリクエストを 1 つ使います。
    つなぎ直しは 1 秒から倍々で 60 秒までです。
    呼び鈴が無い Worker（この版で入れ直していないもの）や、つながらない PC では、起動は今までどおり 30 秒ごとの pull で動き、`/` と `@` の候補だけが出ません。
27. **`@` と `/` の問い合わせは、中身が Worker に見えないように封じて PC へ渡しますが、回数の上限は緩いです。**
    問い合わせの本文（打った文字、ファイルのパス）と答え（ファイル名、スキルの名前と説明）は、スマホ用の鍵で封じます。
    Worker と Durable Object が見られるのは、宛先の PC、時刻、回数、封の大きさだけです。
    PC は、プロジェクトの根の外のパスを返しません。
    1 台のスマホから 10 秒に 20 回までの上限は、Durable Object のメモリで数えるので、眠れば消えます。
    盗まれたスマホのトークンで、PC のプロジェクトのファイル名とスキルの名前を読まれることは防げません（21 の「承諾なしで起こせる」と同じ範囲の権限です）。
28. **画像は封じて R2 に置き、PC が取ったら消します。**
    スマホのトークンが触れる R2 の鍵は、`mobile/<自分の ID>/` の下に置くことだけです。
    PC のトークンは、自分宛ての依頼の画像を読むことだけです。
    1 枚 5 MiB まで、1 件に 4 枚まで、置いたままは 1 台で 40 枚までです。
    PC が答えを返したときに消し、答えが来ないものは 24 時間で消します（スマホが次に画像を置くときと依頼を出すとき、それと Worker の孤児の掃除で消します。孤児の掃除は `mobile/` の下を索引で見ず、24 時間より古いものだけを消すので、解除したスマホの画像も残りません）。
    画像の中身は、スマホ用の鍵で封じてあるので、Worker と R2 は読めません。
29. **Worker をこの版で入れ直すと、Durable Object の `migrations` が当たります。**
    `hangar setup cloud` をもう一度実行すると、`wrangler.jsonc` に Durable Object の束縛と `migrations`（`bell-v1`）が入ります。
    同じ設定で再実行したときは、何も足されません。
    `migrations` は後から追記する形にしてください。
    過去の段を消すと、wrangler が全段を当て直す警告を出します。

## 実測の記録

### 1 台目の作成と起動

0.8.x までの形での実測では、`setup cloud` は 16 秒で終わりました。
0.9.0 では、これにリカバリーキーの保存と末尾 4 文字の入力の時間が加わります（0.9.0 の形では未実測です）。
同期を入れた後も `hangar start` は 1.0 秒から 1.1 秒で、起動が遅くなることはありません（APAC のリージョンで測りました）。

### 設定の同期

実測では、片方の書き換えが相手に降りるまで 10 秒から 30 秒でした。

### やめるとき（`teardown`）

実測では 14 秒から 18 秒で終わりました。

### スマホの受信箱と起動

D1 の書き込みと読み取りの見積もり、Durable Object と R2 の見積もりは `docs/design.md` の「スマホ（試験的）」の末尾にあります。
実測は、1 日使ってから、その表の「実測」の欄に埋めます。
いまは未実測です。
