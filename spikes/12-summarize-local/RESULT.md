# spike 12: LM Studio での要約

判定: 合格（モデルの選定に条件）
実施日: 2026-09-17

## 確かめたこと
- LM Studio の OpenAI 互換 API に、圧縮した本文（5,771 字と 12,000 字）を `response_format: json_schema`（strict）で投げ、3 セッション × 3 モデルを試した。
- **gemma-4-26b-a4b-it-heretic**：3 件ともスキーマどおりの JSON。題名、1 文、本文、状態、次の一手が具体的で、内容も本文に沿っている。
- **qwen3.8-27b-uncensored-mlx**：3 件とも本文が空。`completion_tokens` のほぼ全部が `reasoning_tokens`（思考）で、既定の上限内で思考を終えられず出力に至らなかった。
- **qwen3.6-35b-a3b-mlx**：LM Studio の保護（「システム資源が不足」）で読み込めなかった。

## 計測値
- gemma 26B：初回 57 秒（モデル読み込み込み）、以後 6.3〜6.6 秒（入力 5.7k〜7.1k トークン、出力 140〜200 トークン）。
- qwen 27B：27〜35 秒で本文空。

## 設計への影響
- 既定モデルは gemma 26B のような**思考なしの指示追従モデル**にする。思考モデルを使う場合は `max_tokens` を十分に取り、思考を無効化するオプション（LM Studio 側の設定やモデルのテンプレート引数）を Settings で指定できるようにする。要約器は「本文が空」を失敗として扱い、フォールバックへ回す。
- 6 秒台なら run 終了時の事後生成を待ち時間なしに近い形で出せる。Haiku（20〜40 秒、有料）より速い。
- 初回のモデル読み込みに 1 分近くかかる。Settings の「要約器を試す」ボタンで事前に温められるようにする。
- gemma の `state` は「完了」に寄りがちで、進行中のセッションでも `done` を返した例があった。判定基準（最後のターンが利用者への問いなら `in_progress`）をプロンプトに明示する。

## 残った疑問
- 本文 12,000 字を超える長いセッションの要約品質。中盤の間引きで重要な決定が落ちる可能性があり、フェーズ 3 で「ツール呼び出しの要約行を残す」など圧縮規則を詰める。
